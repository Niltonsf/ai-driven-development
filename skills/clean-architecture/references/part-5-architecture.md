# CA reference: Part V — Architecture

PDF pages 117-207, chapters 15-29. The core of the book: what architecture is
for, where the lines go, what sits inside them, and what a crossing costs.

Skills scoped to this card: `ca-dependency-rule` (22, 19), `ca-boundaries`
(17, 18, 24, 25), `ca-business-rules` (20, 16, 21), `ca-humble-object`
(23, 28), `ca-details` (26).

## Ch.15 — What Is Architecture? [CA ch.15 pp.117-124]

- A software architect is a programmer and continues to be a programmer, taking programming tasks while guiding the rest of the team [CA ch.15 p.117]
- The architecture of a system is the shape given to it: the division into components, their arrangement, and the ways they communicate [CA ch.15 p.117]
- The strategy is to leave as many options open as possible, for as long as possible [CA ch.15 p.118]
- Architecture has very little bearing on whether a system works; the troubles show up in deployment, maintenance and ongoing development [CA ch.15 p.118]
- A goal of architecture is a system that can be easily deployed with a single action [CA ch.15 p.118]
- Almost any operational difficulty can be resolved by throwing more hardware at the system, which is why the cost equation leans toward development, deployment and maintenance [CA ch.15 p.119]
- Architecture should reveal operation: use cases, features and required behaviors are elevated to first-class entities visible to the developers [CA ch.15 p.119]
- The primary cost of maintenance is spelunking and risk [CA ch.15 p.120]
- All software systems decompose into policy and details; the policy holds the business rules and is where the true value lives [CA ch.15 p.120]
- Details are IO devices, databases, web systems, servers, frameworks and communication protocols, which do not impact the behavior of the policy [CA ch.15 p.120]
- A good architect maximizes the number of decisions not made, and pretends a decision already made by someone else has not been made [CA ch.15 p.121]
- Device independence separated policy from detail: the same program could read and write cards or tape without any change [CA ch.15 p.122]
- Good architects separate details from policy so thoroughly that the policy has no knowledge of the details [CA ch.15 p.124]

## Ch.16 — Independence [CA ch.16 pp.125-132]

- A good architecture must support the use cases and operation, the maintenance, the development and the deployment of the system [CA ch.16 p.125]
- Supporting behavior means clarifying and exposing it, so a shopping cart application looks like a shopping cart application [CA ch.16 p.125]
- Conway's law: any organization that designs a system produces a design whose structure copies the organization's communication structure [CA ch.16 p.126]
- The goal for deployment is immediate deployment, without dozens of little configuration scripts and property file tweaks [CA ch.16 p.127]
- Decoupling layers: the UI changes for reasons that have nothing to do with business rules, so the UI portions of a use case are separated from the business rule portions [CA ch.16 p.127]
- Application-specific rules such as field validation and application-independent rules such as interest calculation change at different rates and are separated [CA ch.16 p.128]
- The system divides into decoupled horizontal layers, and use cases are narrow vertical slices that cut through them [CA ch.16 p.128]
- True duplication means every change to one instance requires the same change to every duplicate; false or accidental duplication only looks alike [CA ch.16 pp.129-130]
- Two use cases with similar screen structures are most likely accidental duplication, and unifying them makes them hard to separate later [CA ch.16 p.130]
- Passing a database record straight to the UI instead of creating a view model is almost certainly accidental duplication [CA ch.16 p.130]
- Decoupling modes: source level, deployment level, and service level [CA ch.16 pp.130-131]
- Source level controls dependencies between source modules; components execute in the same address space and communicate with function calls, which people call a monolithic structure [CA ch.16 p.130]
- Deployment level controls dependencies between deployable units such as jar files, DLLs or shared libraries [CA ch.16 p.130]
- Service level reduces dependencies to data structures and communicates solely through network packets [CA ch.16 p.131]
- Decoupling at the service level by default is expensive in development time and system resources, and encourages coarse-grained decoupling [CA ch.16 p.131]
- A good architecture lets a system be born as a monolith and grow into independently deployable units and then services, and allows reversing that progression [CA ch.16 p.131]

## Ch.17 — Boundaries: Drawing Lines [CA ch.17 pp.133-143]

- Software architecture is the art of drawing lines called boundaries, which restrict those on one side from knowing about those on the other [CA ch.17 p.133]
- What saps people-power is coupling, and especially coupling to premature decisions [CA ch.17 p.133]
- Premature decisions are those that have nothing to do with the business requirements: frameworks, databases, web servers, utility libraries, dependency injection [CA ch.17 p.133]
- Company P: a premature three-tier decision multiplied the development effort enormously for a server farm that never existed [CA ch.17 p.134]
- FitNesse deferred the database for over a year by putting an interface between all data accesses and the data repository [CA ch.17 p.136]
- Because there was no database for 18 months, there were no schema, query, server, password or connection-time issues, and the tests ran fast [CA ch.17 p.137]
- You draw lines between things that matter and things that do not: the GUI does not matter to the business rules, and the database does not matter to either [CA ch.17 p.137]
- The business rules need to know only that a set of functions can fetch or save data, which puts the database behind an interface [CA ch.17 p.137]
- The Database knows about the BusinessRules; the BusinessRules do not know about the Database, so the database decision can be deferred [CA ch.17 p.139]
- The IO is irrelevant: the model would happily execute its duties without the game ever being displayed on the screen [CA ch.17 pp.139-140]
- The less relevant component depends on the more relevant one: the GUI cares about the BusinessRules [CA ch.17 p.140]
- The core business rules are kept separate from and independent of components that are optional or can be implemented in many forms, which is a plugin architecture [CA ch.17 p.140]
- ReSharper depends on Visual Studio, a deeply asymmetric relationship: one team cannot disturb the other [CA ch.17 p.141]
- A plugin architecture creates firewalls across which changes cannot propagate [CA ch.17 p.142]
- Boundaries are drawn where there is an axis of change, which is the Single Responsibility Principle telling us where to draw them [CA ch.17 p.142]
- Partition the system into components, then arrange the arrows between them to point toward the core business [CA ch.17 p.142]

## Ch.18 — Boundary Anatomy [CA ch.18 pp.144-148]

- At runtime a boundary crossing is a function on one side calling a function on the other and passing data; the trick is managing the source code dependencies [CA ch.18 p.144]
- The monolith: a disciplined segregation of functions and data within a single processor and a single address space, the source-level decoupling mode [CA ch.18 p.144]
- The boundaries of a monolith are invisible at deployment and still present and meaningful [CA ch.18 p.145]
- The simplest crossing is a call from a low-level client to a higher-level service, where runtime and compile-time dependency point the same way [CA ch.18 p.145]
- When a high-level client invokes a lower-level service, dynamic polymorphism inverts the dependency against the flow of control [CA ch.18 p.145]
- Communications inside a monolith are function calls, very fast and inexpensive, so crossings can be very chatty [CA ch.18 p.146]
- Deployment components are dynamically linked libraries: a .Net DLL, a Java jar file, a Ruby Gem, a UNIX shared library; deployment does not involve compilation [CA ch.18 p.146]
- Threads are not architectural boundaries or units of deployment, but a way to organize the schedule and order of execution [CA ch.18 p.147]
- Local processes run in separate address spaces and communicate through sockets or other operating system facilities; crossings are moderately expensive, so chattiness is limited [CA ch.18 p.147]
- The source code of a higher-level process must not contain the names, physical addresses or registry lookup keys of lower-level processes [CA ch.18 p.147]
- Services are the strongest boundary; communications are very slow compared to function calls, with turnaround from tens of milliseconds to seconds [CA ch.18 p.148]
- The source code of higher-level services must not contain physical knowledge, such as a URI, of any lower-level service [CA ch.18 p.148]
- Most systems use more than one boundary strategy, mixing chatty local boundaries with boundaries concerned about latency [CA ch.18 p.148]

## Ch.19 — Policy and Level [CA ch.19 pp.149-152]

- A computer program is a detailed description of the policy by which inputs are transformed into outputs [CA ch.19 p.149]
- Policies that change for the same reasons and at the same times are at the same level and belong in the same component [CA ch.19 p.149]
- The components are formed into a directed acyclic graph whose edges are source code, compile-time dependencies: import, using or require statements [CA ch.19 p.149]
- Low-level components are designed so that they depend on high-level components [CA ch.19 p.150]
- Level is the distance from the inputs and outputs; the farther a policy is from both, the higher its level [CA ch.19 p.150]
- Data flows and source code dependencies do not always point the same way: dependencies are decoupled from data flow and coupled to level [CA ch.19 p.150]
- Writing the encryption program as one function that calls readChar and writeChar is incorrect architecture, because the high-level function depends on lower-level ones [CA ch.19 pp.150-151]
- Higher-level policies change less frequently and for more important reasons than lower-level ones [CA ch.19 p.151]
- Lower-level components should be plugins to the higher-level components [CA ch.19 p.152]

## Ch.20 — Business Rules [CA ch.20 pp.153-157]

- Critical Business Rules make or save the business money, and would exist even if there were no system to automate them [CA ch.20 p.153]
- Critical Business Data is the data those rules require, which would exist even if the system were not automated [CA ch.20 p.153]
- An Entity embodies a small set of Critical Business Rules operating on Critical Business Data [CA ch.20 p.154]
- The Entity is pure business and nothing else, unsullied by concerns about databases, user interfaces or third-party frameworks [CA ch.20 p.154]
- An Entity does not require an object-oriented language: the requirement is to bind the critical data and critical rules in a single separate module [CA ch.20 p.154]
- A use case is a description of the way an automated system is used: the input, the output, and the processing steps that produce it [CA ch.20 p.155]
- Use cases contain application-specific business rules, and control the dance of the Entities [CA ch.20 p.155]
- From the use case it is impossible to tell whether the application is delivered on the web, a thick client, a console or a pure service [CA ch.20 p.155]
- Entities have no knowledge of the use cases that control them; use cases depend on Entities, Entities do not depend on use cases [CA ch.20 p.156]
- Entities are higher level because they are generalizations usable by many applications, and so are farther from the inputs and outputs [CA ch.20 p.156]
- The use case class accepts simple request data structures for its input and returns simple response data structures as its output [CA ch.20 p.156]
- Request and response models do not derive from framework interfaces such as HttpRequest and HttpResponse, and know nothing of the web [CA ch.20 p.156]
- Request and response models must not contain references to Entity objects: they change for different reasons, and tying them together violates the CCP and the SRP [CA ch.20 p.156]
- Business rules are the family jewels, and should be the most independent and reusable code in the system [CA ch.20 p.156]

## Ch.21 — Screaming Architecture [CA ch.21 pp.158-160]

- The plans of a building scream what the building is, and the top-level directory structure of an application should scream what the application is [CA ch.21 p.158]
- Architectures should not be supplied by frameworks: frameworks are tools to be used, not architectures to be conformed to [CA ch.21 p.159]
- If your architecture is based on frameworks, it cannot be based on your use cases [CA ch.21 p.159]
- Good architectures are centered on use cases, so the architect can describe the supporting structures without committing to frameworks, tools and environments [CA ch.21 p.159]
- The web is a delivery mechanism, an IO device, and the decision to deliver over it should be deferred [CA ch.21 p.159]
- Look at each framework with a jaded eye, and ask how to protect yourself from it [CA ch.21 p.160]
- If the frameworks are kept at arm's length, all the use cases can be unit-tested without the web server running or the database connected [CA ch.21 p.160]
- This chapter prescribes no folder tree: it asks what the top-level directory structure and the highest-level package say about the system [CA ch.21 p.158]

## Ch.22 — The Clean Architecture [CA ch.22 pp.161-166]

- Hexagonal Architecture (Ports and Adapters), DCI and BCE all have the same objective, the separation of concerns, achieved by dividing the software into layers [CA ch.22 p.161]
- The resulting systems are independent of frameworks, testable, independent of the UI, independent of the database, and independent of any external agency [CA ch.22 pp.161-162]
- The Dependency Rule: source code dependencies must point only inward, toward higher-level policies [CA ch.22 p.162]
- Nothing in an inner circle can know anything at all about something in an outer circle, including the name of any function, class or variable declared there [CA ch.22 p.162]
- Data formats declared in an outer circle should not be used by an inner circle, especially formats generated by a framework [CA ch.22 p.162]
- Entities encapsulate enterprise-wide Critical Business Rules and are the least likely to change when something external changes [CA ch.22 p.163]
- The use cases layer orchestrates the flow of data to and from the entities and directs them to use their Critical Business Rules [CA ch.22 p.163]
- Interface adapters convert data from the format convenient for use cases and entities to the format convenient for an external agency [CA ch.22 p.163]
- The MVC of a GUI is wholly contained in the interface adapters layer: presenters, views and controllers all belong there [CA ch.22 p.163]
- If the database is a SQL database, all SQL is restricted to the interface adapters layer [CA ch.22 p.163]
- The outermost layer is frameworks and drivers, where all the details go: the web is a detail, the database is a detail [CA ch.22 p.164]
- The circles are schematic: there is no rule that says there must always be just these four, and the Dependency Rule always applies [CA ch.22 p.164]
- A use case that needs to call the presenter calls an output port interface in the inner circle, which the presenter in the outer circle implements [CA ch.22 p.164]
- Dynamic polymorphism creates source code dependencies that oppose the flow of control, whichever direction the flow of control travels [CA ch.22 p.164]
- The data that crosses a boundary is a simple data structure, and it is always in the form most convenient for the inner circle [CA ch.22 pp.164-165]
- Entity objects and database rows are not passed across a boundary; a row structure passed inward would violate the Dependency Rule [CA ch.22 pp.164-165]
- In the typical scenario the Controller packages input into a plain object, passes it through the InputBoundary to the UseCaseInteractor, which returns OutputData through the OutputBoundary to the Presenter [CA ch.22 p.165]
- The Presenter repackages the OutputData into the ViewModel, leaving the View with almost nothing to do other than move data into the HTML page [CA ch.22 pp.165-166]

## Ch.23 — Presenters and Humble Objects [CA ch.23 pp.167-170]

- The Humble Object pattern splits behaviors into two modules: one humble module holding the hard-to-test behaviors, and one holding the testable behaviors [CA ch.23 p.167]
- The View is the humble object that is hard to test: it moves data into the GUI but does not process that data [CA ch.23 p.168]
- The Presenter is the testable object: it accepts data from the application and formats it so the View can simply move it to the screen [CA ch.23 p.168]
- Everything that appears on the screen is represented in the View Model as a string, a boolean or an enum [CA ch.23 p.168]
- The separation into testable and non-testable parts often defines an architectural boundary [CA ch.23 p.168]
- Database gateways are polymorphic interfaces with methods for every create, read, update or delete operation the application performs [CA ch.23 p.168]
- SQL is not allowed in the use cases layer; the gateway implementation in the database layer is the humble object [CA ch.23 pp.168-169]
- Interactors are not humble, because they encapsulate application-specific business rules, and they stay testable because gateways are replaced with stubs and test-doubles [CA ch.23 p.169]
- ORMs are better named data mappers, and belong in the database layer as another Humble Object boundary between the gateway interfaces and the database [CA ch.23 p.169]
- Service listeners receive data from the service interface and format it into a simple data structure the application can use [CA ch.23 p.169]
- At each architectural boundary the Humble Object pattern is lurking somewhere nearby [CA ch.23 p.169]

## Ch.24 — Partial Boundaries [CA ch.24 pp.171-173]

- Full-fledged boundaries are expensive: reciprocal polymorphic interfaces, input and output data structures, and the dependency management to keep both sides independently deployable [CA ch.24 p.171]
- A partial boundary holds the place for a boundary that might be needed later [CA ch.24 p.171]
- Skip the last step: do all the work of independently deployable components, then keep them in a single component, with no version tracking or release management burden [CA ch.24 pp.171-172]
- The danger of skipping the last step: as it becomes clear the separation is never needed, dependencies start to cross the line in the wrong direction [CA ch.24 p.172]
- One-dimensional boundary: the Strategy pattern, an interface used by clients and implemented by a service class, with the dependency inversion already in place [CA ch.24 p.172]
- Without reciprocal interfaces nothing prevents a backchannel other than the diligence and discipline of the developers and architects [CA ch.24 p.173]
- Facade: even the dependency inversion is sacrificed, and the client has a transitive dependency on all the service classes [CA ch.24 p.173]
- Deciding where a boundary might one day exist, and whether to implement it fully or partially, is one of the functions of an architect [CA ch.24 p.173]

## Ch.25 — Layers and Boundaries [CA ch.25 pp.174-180]

- Three components, UI, business rules and database, is enough for some simple systems and not for most [CA ch.25 p.174]
- Hunt the Wumpus: the game rules communicate with the UI through a language-independent API, so any number of UI components can reuse them [CA ch.25 pp.174-175]
- Language is not the only axis of change for the UI: the mechanism that delivers the text is another, and another potential boundary [CA ch.25 p.176]
- The API is defined and owned by the user, rather than by the implementer [CA ch.25 p.176]
- Orienting the diagram so all arrows point up puts the component with the highest-level policies at the top [CA ch.25 p.177]
- The organization divides the flow of data into streams, one for communicating with the user and one for persistence, meeting at the top [CA ch.25 p.177]
- Adding a network component divides the data flow into three streams [CA ch.25 pp.177-178]
- Splitting the streams: a higher-level policy that manages the player's health sits above the lower-level policy that manages the map [CA ch.25 p.178]
- Architectural boundaries exist everywhere, and the architect must recognize when they are needed [CA ch.25 pp.179-180]
- Boundaries fully implemented are expensive, and boundaries ignored are very expensive to add later, even with comprehensive test-suites and refactoring discipline [CA ch.25 p.180]
- The decision is not made once: watch the system evolve, and implement a boundary at the inflection point where the cost of implementing becomes less than the cost of ignoring [CA ch.25 p.180]

## Ch.26 — The Main Component [CA ch.26 pp.181-184]

- In every system there is at least one component that creates, coordinates and oversees the others, called Main [CA ch.26 p.181]
- Main is the ultimate detail, the lowest-level policy, and the initial entry point of the system [CA ch.26 p.181]
- Nothing other than the operating system depends on Main [CA ch.26 p.181]
- Main creates all the Factories, Strategies and other global facilities, then hands control over to the high-level abstract portions of the system [CA ch.26 p.181]
- Dependencies are injected in Main by a Dependency Injection framework, and Main distributes them afterward without using the framework [CA ch.26 p.181]
- Main is the dirtiest of all the dirty components [CA ch.26 p.181]
- Main loads the strings that the main body of the code should not know about [CA ch.26 p.181]
- Main uses a factory with a class name so that changes in that dirtier class do not cause Main to recompile or redeploy [CA ch.26 pp.182-183]
- Main is a plugin to the application, so there can be many Main components, one per configuration: Dev, Test, Production, or one per country or customer [CA ch.26 p.184]

## Ch.27 — Services: Great and Small [CA ch.27 pp.185-191]

- Services in themselves do not define an architecture: they are function calls across process or platform boundaries, and some are architecturally significant [CA ch.27 pp.185-186]
- The decoupling fallacy: services are decoupled at the level of individual variables, and strongly coupled by the data they share [CA ch.27 p.186]
- The fallacy of independent development and deployment: where services are coupled by data or behavior, development and deployment must be coordinated [CA ch.27 pp.186-187]
- The kitty problem: a new cross-cutting feature forces a change in every service of a functional decomposition [CA ch.27 p.188]
- The component-based answer uses classes that are polymorphically extended, with the new feature in its own component following the Dependency Rule [CA ch.27 p.188]
- Services do not need to be little monoliths: they can be given an internal component structure so new components are added without changing existing ones [CA ch.27 pp.189-190]
- Architectural boundaries do not fall between services; they run through the services, dividing them into components [CA ch.27 p.190]

## Ch.28 — The Test Boundary [CA ch.28 pp.192-194]

- Tests are part of the system and participate in the architecture like every other part [CA ch.28 p.192]
- From an architectural point of view all tests are the same, whether tiny TDD tests or large FitNesse, Cucumber, SpecFlow or JBehave tests [CA ch.28 p.192]
- Tests follow the Dependency Rule and always depend inward toward the code being tested; think of them as the outermost circle [CA ch.28 p.192]
- Nothing within the system depends on the tests, and they are the most isolated system component [CA ch.28 pp.192-193]
- Tests strongly coupled to the system must change along with it, which is the Fragile Tests Problem [CA ch.28 p.193]
- Fragile tests make the system rigid: developers resist changes that would break a thousand tests [CA ch.28 p.193]
- The first rule of software design, for testability as for anything else: do not depend on volatile things, and GUIs are volatile [CA ch.28 p.193]
- The testing API lets the tests verify business rules while avoiding security constraints, bypassing expensive resources such as databases, and forcing the system into testable states [CA ch.28 p.193]
- The purpose of the testing API is to decouple the structure of the tests from the structure of the application [CA ch.28 p.194]
- Structural coupling: a test class for every production class and a test method for every production method makes the tests fragile and the production code rigid [CA ch.28 p.194]
- Tests tend to become more concrete and specific while production code becomes more abstract and general, and structural coupling impedes that evolution [CA ch.28 p.194]
- The superpowers of the testing API are dangerous in production, so they belong in a separate, independently deployable component [CA ch.28 p.194]

## Ch.29 — Clean Embedded Architecture [CA ch.29 pp.195-207]

- Although software does not wear out, it can be destroyed from within by unmanaged dependencies on firmware and hardware [CA ch.29 p.195]
- Code is firmware not because of where it is stored, but because of what its dependencies are and how hard it is to change as hardware evolves [CA ch.29 p.196]
- Non-embedded developers write firmware too, whenever they bury SQL in their code or spread platform dependencies throughout it [CA ch.29 p.196]
- The App-titude test: code written only to make it work, with no structure for a long useful life [CA ch.29 p.197]
- The target-hardware bottleneck: code that can be tested only on the target slows development down [CA ch.29 p.199]
- The hardware abstraction layer is the boundary between the software and the firmware, and its API is tailored to the software's needs [CA ch.29 p.201]
- The HAL provides a service and does not reveal how it does it: flash storage is a detail hidden from the software [CA ch.29 p.201]
- Do not reveal hardware details to the user of the HAL; a successful HAL provides the substitution points that make off-target testing possible [CA ch.29 p.202]
- The processor is a detail: vendor extensions to C tie code to one tool chain, so few files are allowed to know about them [CA ch.29 pp.202-203]
- The operating system is a detail: an operating system abstraction layer isolates the software from the OS [CA ch.29 p.205]
- Layers interact through interfaces, which makes each interface a substitution point for off-target testing [CA ch.29 p.206]
- Thousands of repetitions of a conditional compilation directive naming the board version violate the DRY principle; a HAL hides the hardware type instead [CA ch.29 pp.206-207]
