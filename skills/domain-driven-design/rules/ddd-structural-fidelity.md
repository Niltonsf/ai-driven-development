# DDD rule: structural fidelity

Language is free. Structure is not.

## There is no language halt in this pack

The Preface releases the language:

```ddd-quote [DDD pref. p.21]
All the code samples presented in the book are implemented in the C# language.
```

The same page states the concepts and techniques are not limited to the C#
language or to the object-oriented programming approach, and that everything is
relevant for other languages and other programming paradigms [DDD pref. p.21]
`RULE`. Chapter 6 repeats it for functional programming:

```ddd-quote [DDD ch.6 p.103]
the discussed concepts are not limited to OOP and are as relevant for the functional programming paradigm
```

Therefore **this pack has no `CODE_STYLE_DIVERGENCE` code**. A request for
TypeScript, Python, Go, Kotlin or anything else is legitimate and is answered.
Do not copy the sibling pack's language halt; it would contradict this book.

Which languages the book itself prints is a fact, not a limit:
`../references/ddd-code-listings.md`, generated by
`python3 tools/ddd_pdf.py listings`.

## The closed structural checklist

A request whose code would break one of these halts with
`STRUCTURE_DIVERGENCE`, naming the page. The list is closed: nothing else halts
for structure.

1. A mutable value object: value objects are implemented as immutable objects [DDD ch.6 p.107] `RULE`
2. An explicit identification field on a value object: a value object can be identified by the composition of its values and thus does not require an explicit identification field [DDD ch.6 p.108] `RULE`
3. A public setter on an aggregate: an aggregate can only be modified by its own methods [DDD ch.6 p.121] `RULE`
4. A public setter left on an active record during the refactoring: make all of the active records' setters private so that they can only be modified from inside the active record itself [DDD ch.11 p.200] `RULE`
5. Two aggregate instances modified in one transaction: a change to an aggregate's state can only be committed individually, one aggregate per database transaction [DDD ch.6 p.113] `RULE`
6. An object reference held to an aggregate outside the boundary: external aggregates are referenced by ID to ensure that each aggregate has its own transactional boundary [DDD ch.6 p.116] `RULE`
7. A domain event published from inside the aggregate: publishing the domain event right from the aggregate is bad for two reasons [DDD ch.9 p.170] `RULE`
8. A domain event published by the application layer straight after the database commit: the outbox pattern ensures reliable publishing of domain events [DDD ch.9 p.171] `RULE`
9. A writable read model: read models are read-only, and none of the system's operations can directly modify the read models' data [DDD ch.8 p.156] `RULE`
10. Business logic in the service layer rather than the aggregate: the service layer would go on a very strict diet, and all the business logic would be refactored into the corresponding aggregates [DDD app.A p.303] `RULE`
11. An ORM, rather than the aggregate, defining the transactional scope: instead of an ORM, each aggregate itself would define the transactional scope [DDD app.A p.303] `RULE`

Item 5 is restated as a question the book answers in the field:

- Why can't a database transaction modify more than one instance of an aggregate? To ensure that the consistency boundaries are correct [DDD ch.13 p.238] `RULE`

## Prefer no code at all

Boundaries, dependency direction, consistency scope and pattern selection are
language-independent in this book. Code is the exception, not the deliverable. A
skill emits code only when the request asks for code.
